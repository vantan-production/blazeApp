## 1. 背景と目的

本アプリは以下のデータを保持するが、2026-09-04 時点でバックアップの設計・運用ルールが存在しない。

- 管理者アカウント、ニュース／メディア／実績／試合風景の投稿
- 一般利用者から届いた**問い合わせ**と**体験申し込み**（氏名・生年月日・電話番号・学校名を含む個人情報）
- 試合風景の写真（**未成年を含む肖像**。掲載同意ステータスとモザイクで管理）

これらは再取得が不可能なデータであり、消失した場合に代替手段がない。本書はその保護方針・保持期間・復旧手順を定義する。

### 本書が解決する具体的な問題

1. RDS の自動バックアップ保持期間が **1日**しかなく、週末に起きた事故に月曜日気づいても戻せない。
2. S3 にバージョニングがなく、アプリの**正常系の操作そのものが不可逆**である（3-3 参照）。
3. AWS アカウント／リージョンレベルの障害に対する備えが皆無である。
4. 「どこまで戻せるのか」「誰がどう戻すのか」が誰にも共有されていない。

## 2. 用語

| 用語 | 定義 |
|---|---|
| RPO（Recovery Point Objective） | 障害時に許容する**データ損失の最大時間**。「何分前の状態まで戻せるか」 |
| RTO（Recovery Time Objective） | 障害発生から**サービス復旧までに許容する時間** |
| PITR（Point-in-Time Recovery） | 任意の時刻の状態へ復元する機能。RDS では自動バックアップ有効時にトランザクションログから復元する |
| 物理バックアップ | RDS スナップショット。ブロックレベルの複製。同一エンジン・同一サービス上でのみ復元可能 |
| 論理バックアップ | `pg_dump` による出力。SQL 論理表現。他環境・他クラウド・ローカルでも復元可能 |
| 3-2-1 ルール | データを **3コピー**、**2種類の形式／媒体**、うち **1つをオフサイト**に置く |
| 3-2-1-1-0 ルール | 上記に **1つをイミュータブル（改変・削除不可）**、**復元検証エラー0** を加えた現代版。本書はこちらを採用する |

### 3-2. prod と dev が同一 RDS インスタンスを共有している

Secrets Manager の値（認証情報をマスクして確認）:

```
prod: postgresql://***@blaze-app-db.***.ap-northeast-1.rds.amazonaws.com:5432/postgres
dev : postgresql://***@blaze-app-db.***.ap-northeast-1.rds.amazonaws.com:5432/blazeapp_dev
```

**データベース名が違うだけで物理インスタンスは同一**。`infra/lib/backend-stack.ts` のコメントにある「dev への変更が prod に影響することはない」は VPC・ECS・ALB については正しいが、DB については成立していない。

バックアップ観点での影響は重大で、**RDS の PITR / スナップショット復元はインスタンス単位**である。したがって「prod を昨日の状態に戻す」操作は dev も同時に巻き戻す。逆に dev 側の事故（`DROP DATABASE` の打ち間違い等）が prod の隣で発生する。

→ **本書は prod / dev の DB 分離を前提として記述する**（9-1 参照）。

## 4. 保護目標と、目標を制約する技術的事実

### 4-1. RPO / RTO

| 区分 | 目標 | 適用シナリオ |
|---|:-:|---|
| **一次 RPO** | **1時間**（実力値は PITR の粒度で約5分） | 誤操作・アプリのバグ・DB 障害・AZ 障害 |
| **二次 RPO** | **1時間** | AWS アカウント侵害・リージョン全損・KMS キー消失など、同一リージョンのバックアップ機構ごと失われるケース |
| **RTO** | **4時間** | 全シナリオ共通 |

二次 RPO を一次と同じ1時間に置くため、論理バックアップ（`pg_dump`）を**毎時**取得する（5-2）。一般的にはここを24時間（日次）とする設計が多いが、本アプリのデータ量では毎時取得のコスト増が月1ドル未満に収まるため、目標を揃える方が運用ルールとして単純で説明もしやすい。

### 4-2. 対象資産の分類

| 資産 | 再取得可能性 | バックアップ | 理由 |
|---|---|:-:|---|
| RDS のデータ | **不可能** | **必須** | 投稿・問い合わせ・体験申し込み・アカウント |
| S3 の画像／動画／ファイル | **不可能** | **必須** | 撮影しなおせない。DB には `path` しか無く実体は S3 のみ |
| Redis（Upstash） | 不要 | **対象外** | レートリミットのカウンタのみ。消失しても最大1分間だけ制限が緩むだけ |
| ECS / ALB / VPC | コードから再作成可能 | **対象外** | `infra/` の CDK コードが git にある。ステートレス |
| Secrets Manager | 手動再入力で復旧可 | **限定的に対象** | 5-5 参照。AWS 標準の30日削除猶予に依存する |
| CloudWatch Logs | 不可能だが業務データではない | **対象外** | 現行の保持期間（14日）を維持 |
| ECR のコンテナイメージ | git から再ビルド可能 | **対象外** | `back/Dockerfile` から再現できる |

### 4-3. 【重要】AWS マネージドキー暗号化という制約

RDS `blaze-app-db` は **`alias/aws/rds`（AWS マネージドキー）**で暗号化されている。これにより次の制約が生じる。

- **AWS Backup によるクロスリージョン／クロスアカウントのスナップショットコピーが利用できない。** AWS マネージドキーで暗号化されたスナップショットはコピー対象外である。
- **稼働中インスタンスの KMS キーは変更できない。** カスタマー管理キー（CMK）へ移行するには、スナップショットをコピーする際に CMK で再暗号化し、そこから**インスタンスを作り直す**必要がある。
- RDS API の `copy-db-snapshot` によるクロスリージョンコピーが AWS マネージドキー暗号化のスナップショットで成立するかは、**実機で要検証**（宛先リージョン側の CMK 指定が必要）。

**結論**: スナップショット層だけでは 3-2-1 の「1つをオフサイト」を満たせない。**`pg_dump` の論理バックアップを別リージョンの S3 へ置く経路が、オフサイトコピーの実質的な唯一の担い手**となる。3-2-1 を採りたいというご要望は、この構成では技術的にも必然である。

CMK への移行は 9-1 の prod / dev 分離（＝インスタンス再作成を伴う）と**同時に実施すれば追加のダウンタイムなしで完了する**ため、本書ではそれを推奨する。

## 5. バックアップ方式

### 5-0. 3-2-1-1-0 の割り当て

| ルール | 本設計での実体 |
|---|---|
| **3** コピー | ①本番（RDS 本体 / S3 本体） ②同一リージョンの保護層（PITR・スナップショット・S3 非現行バージョン） ③別リージョンの複製（pg_dump / S3 レプリカ） |
| **2** 形式 | 物理（RDS スナップショット：ブロックレベル）＋ 論理（`pg_dump -Fc`：他環境でも復元可能） |
| **1** オフサイト | 大阪リージョン `ap-northeast-3`（ダンプ・画像とも S3 レプリケーションで複製する） |
| **1** イミュータブル | ダンプ保管バケットに **S3 Object Lock（Governance モード）** を適用し、保持期間内は削除・上書き不可にする |
| **0** エラー | 週次の自動リストア検証（8章）。検証に通っていないバックアップは「無い」ものとして扱う |

### 5-1. RDS 物理バックアップ（一次 RPO を担う層）

| 項目 | 設定値 |
|---|---|
| 自動バックアップ保持期間 | **7日**（現状1日から変更） |
| PITR | 有効（保持期間内の任意の時刻、粒度およそ5分） |
| バックアップウィンドウ | **19:00-19:30 UTC（＝ JST 04:00-04:30）**（現状 14:16-14:46 UTC ＝ JST 23:16 は利用時間帯にあたるため変更） |
| メンテナンスウィンドウ | **thu 20:00-20:30 UTC（＝ JST 木 05:00-05:30）** |
| スナップショットへのタグ伝播 | 有効（現状のまま） |
| 削除保護 | **有効化**（現状無効） |
| Multi-AZ | **無効のまま**。RTO 4時間は単一 AZ の復元で満たせるため、月額倍増に見合わないと判断する |

### 5-2. RDS 論理バックアップ = `pg_dump`（二次 RPO とオフサイトを担う層）

| 項目 | 設定値 |
|---|---|
| 実行方式 | **ECS Fargate のスケジュールタスク**（EventBridge Scheduler → `RunTask`）。既存の `BlazeAppBackendStack-prod` の VPC 内から実行する |
| コンテナイメージ | `postgres:18-alpine`（**サーバの 18.3 と同一メジャーの `pg_dump` が必要**。`back/Dockerfile` の `node:20-alpine` には含まれないため専用イメージとする） |
| 実行頻度 | **毎時00分**（二次 RPO 1時間） |
| コマンド | `pg_dump -Fc`（カスタム形式・圧縮あり）→ `aws s3 cp` |
| 保存先 | `s3://blazeapp-db-backups-910972977659-ap-northeast-1/`（**東京**、新規作成）に書き込み、**S3レプリケーションで大阪 `blazeapp-db-backups-910972977659-ap-northeast-3` へ複製**する（13-1 #6）。<br>大阪へ直接書かないのは、S3 Gateway エンドポイント（無料）が同一リージョンにしか到達できず、クロスリージョン転送には NAT か Interface エンドポイントが要るため |
| キー命名 | `hourly/YYYY/MM/DD/blazeapp-YYYYMMDDTHHmmssZ.dump` / `daily/...` / `weekly/...` |
| 認証情報 | ECS タスクロール（IAM）。Secrets Manager から `DATABASE_URL` を取得する。**アクセスキーは使わない** |
| ネットワーク | ECS タスクはプライベートサブネット。**S3 Gateway エンドポイント（無料）**経由で東京バケットへ書く。**NAT ゲートウェイは置かない**（13-1 #6） |
| 暗号化 | SSE-KMS（**カスタマー管理キー**。東京・大阪の各リージョンに1つずつ作成する） |
| Object Lock | **Governance モード**（東京・大阪の両バケット）。`hourly` 48時間 / `daily` 30日 / `weekly` **35日** |
| 失敗検知 | タスク終了コード非0、または想定時刻にオブジェクトが増えていない場合に CloudWatch アラーム → **SNSトピック → メール2〜3件**（13章 #1で決定） |

補足: 論理バックアップにはスキーマも含まれるため、`back/drizzle/` のマイグレーション適用ミスからの巻き戻しにも使える。起動時にマイグレーションを自動適用する実装（`back/src/db/migrate.ts`）である以上、この層は事実上の必須要件になる。

### 5-3. S3（画像・動画・ファイル）

| 項目 | 設定値 |
|---|---|
| バージョニング | **有効化**（prod バケット。運用データ投入前に実施すること） |
| 非現行バージョンの保持 | **30日**でライフサイクル削除 |
| 不完全マルチパートアップロード | 7日で中止・削除 |
| クロスリージョンレプリケーション（CRR） | prod バケット → `blazeapp-storages-replica-910972977659-ap-northeast-3`（新規作成）へ複製 |
| 削除マーカーの複製 | **無効**（`DeleteMarkerReplication: Disabled`）。本番側の削除を複製先に伝播させないことで、誤削除・悪意ある削除に耐える |
| 複製先の保持 | 現行バージョンは無期限、非現行は30日 |
| パブリックアクセスブロック | **4項目すべて有効化**（現状すべて無効。配信は署名付き URL のみで行っており、公開アクセスは不要） |

### 5-4. dev 環境

dev はバックアップ対象外とする。理由は、投入されるデータが検証用であり再作成可能なため。

- dev の RDS: 自動バックアップ保持 **1日**（AWS の最低値。0 にすると PITR が無効になり、誤って本番相当の作業をした際に何も残らないため 1 は残す）
- dev の S3: バージョニングのみ有効化、非現行 **7日**。レプリケーションは行わない

### 5-5. Secrets Manager

- 値そのもののバックアップは取らない。**AWS 標準の削除猶予（30日）**と、`infra/scripts/create-secret.sh` による再作成手順に依存する。
- ただし現状 `create-secret.sh` は「実行者が値を持っていること」を前提にしている。**値の保管場所（パスワードマネージャ等）を運用ルールとして定めること**を必須とする（13-1 #4。Bitwarden に保管する）。
- 未使用の旧シークレット `blazeapp/backend` は削除する（30日の復元猶予つきで消える）。

## 7. 復旧手順（シナリオ別）

### 復旧作業を始める前に — 手動スナップショットの取得

いずれの手順も**着手前に必ず現状のスナップショットを手動で取得する**。

「手動スナップショット」とは、**その時点の RDS インスタンス全体を丸ごと複製した、自分で名前を付けた静止点**のこと。自動バックアップ（PITR・自動スナップショット）とは別枠で保存され、以下の点が異なる。

| | 自動スナップショット | 手動スナップショット |
|---|---|---|
| 作成 | RDS が毎日バックアップウィンドウに自動作成 | **人がコマンドで明示的に作成** |
| 保持 | 保持期間（本設計では7日）を過ぎると**自動削除** | **消すまで残る**（保持期間の対象外） |
| インスタンス削除時 | 一緒に消える | **残る** |
| 用途 | 日常的な巻き戻し | 作業前の退避、長期保管 |

なぜ復旧作業の前に必要かというと、**復旧作業そのものが失敗しうる**ため。「壊れた状態」を戻そうとして、もっと戻せない状態にしてしまう事故は珍しくない（復元先を間違える、`pg_restore` を本番に流してしまう、途中で中断する等）。作業前の断面が手元にあれば、最悪でもそこへ戻ってやり直せる。

```bash
aws rds create-db-snapshot \
  --db-instance-identifier blaze-app-db \
  --db-snapshot-identifier blaze-app-db-before-recovery-$(date +%Y%m%d%H%M) \
  --region ap-northeast-1
```

作成完了（`available`）までは数分かかる。**完了を待ってから復旧作業に着手する**こと。

```bash
aws rds wait db-snapshot-available \
  --db-snapshot-identifier <上で付けた名前> \
  --region ap-northeast-1
```

復旧が無事に終わり、しばらく（目安1週間）運用して問題が出なければ、この手動スナップショットは削除してよい（`aws rds delete-db-snapshot`）。放置すると保管料がかかり続けるため、8章の履歴表に「いつ作ったか・いつ消したか」を記録しておく。

なお S3 側には同じ意味の機能が無い。代わりに**バージョニングが常時オンになっていること**が前提であり、作業前に何かを退避する必要はない（削除しても非現行バージョンとして残るため）。

### シナリオ A: 投稿を1件、誤って削除した（最も高頻度）

1. PITR で**別名の新規インスタンス**に、削除前の時刻を指定して復元する（本番インスタンスは触らない）。
2. 復元先から該当行を `SELECT` し、本番へ `INSERT` で戻す。
3. 画像の実体は S3 のバージョニングから復元する（削除マーカーを削除する）。
4. 復元用インスタンスを削除する。

**想定所要時間: 60〜90分**

### シナリオ B: DB が破損・全損した

1. 影響範囲と「どの時刻まで戻すか」を決定（30分）。
2. PITR または最新スナップショットから新規インスタンスを復元（20GB で30〜60分）。
3. Secrets Manager の `DATABASE_URL` を新エンドポイントへ更新（`infra/scripts/create-secret.sh`）。
4. ECS サービスを強制デプロイして新しい接続先を読み込ませる（10分）。起動時に未適用マイグレーションが自動適用される点に注意。
5. `/health` と主要画面で動作確認（30分）。

**想定所要時間: 約3時間（RTO 4時間内）**

### シナリオ C: リージョン障害／アカウントレベルの事故で ap-northeast-1 が使えない

1. ap-northeast-3 に RDS インスタンスを新規作成（30分）。
2. 大阪の S3（東京から複製されたもの）にある最新の `pg_dump` を `pg_restore` で流し込む（30分）。
   複製には数分のラグがあるため、**東京が完全に失われた直後は最新1〜2件が未複製の可能性がある**。存在するダンプのうち最新のものを使う。
3. `infra/` の CDK を `ap-northeast-3` 向けにデプロイ（30〜60分）。
4. S3 レプリカバケットを参照するよう Secrets を更新し、フロント（Vercel）の API URL を切り替える（30分）。

**想定所要時間: 約3時間（RTO 4時間内）／データ損失は最大1時間（二次 RPO）**

### シナリオ D: モザイクを誤った座標で適用した

S3 バージョニングから直前バージョンを復元する。`docs/role-design.md` Phase 3 の `original_path` 対応が入れば、アプリ機能として原本から再適用できるようになる（バックアップに頼らない本来の解決策）。

### シナリオ E: 掲載取り下げ依頼を受けた画像が、バックアップに残っている

10章の方針に従う（個別削除は行わない）。

## 9. 本設計の前提となる構成変更

以下はバックアップ設定の**前提条件**であり、これらが未対応のままではバックアップを整えても効果が限定的になる。

### 9-1. prod / dev の DB 分離ならびに CMK 化（必須）

3-2 のとおり現状は単一インスタンスの共有である。また 4-3 のとおり CMK 化にはインスタンス再作成が必要。**この2つは同じ「作り直し」作業で同時に解決できる**ため、まとめて実施する。

想定手順:
1. 現行インスタンスのスナップショットを取得する。
2. スナップショットを CMK で再暗号化してコピーする。
3. コピーから prod 用インスタンスを新規作成する（`PubliclyAccessible: false`、CDK の VPC 内、削除保護有効）。
4. dev 用は別インスタンスを新規作成し、`blazeapp_dev` のダンプを流し込む。
5. Secrets Manager の `DATABASE_URL` を両 stage とも更新する。
6. 旧インスタンスは1週間程度残してから削除する。

### 9-2. RDS のネットワーク是正（必須）

現状 `0.0.0.0/0` から 5432 が到達可能で、防御はパスワードのみである。**バックアップは「消された後」に効く仕組みであり、「消されにくくする」対策の代わりにはならない。**

- `PubliclyAccessible: false` にする
- SG のインバウンドを ECS タスクの SG からのみに限定する
- RDS を CDK の VPC（`vpc-0c13f142b5ca4ca31`）内へ移す。**`natGateways: 0` は維持したままでよい**（13-1 #6）。
  pg_dump タスクの S3 への書き込みは、同一リージョン向けの S3 Gateway エンドポイント（無料）で賄えるため、NAT ゲートウェイは不要

### 9-3. root アクセスキーの廃止（必須・バックアップ範囲外）

現在ローカルの AWS CLI が root アカウントのアクセスキーで動作している（`Arn: arn:aws:iam::910972977659:root`）。この鍵が漏れた場合、バックアップを含む**すべてのリソースを削除できる**ため、3-2-1 の前提が崩れる。IAM ユーザー／ロールへ移行し、root のアクセスキーは削除すること。

### 9-4. S3 パブリックアクセスブロックの有効化 ✅ **適用済み（2026-09-10）**

配信は署名付き URL で行っており公開アクセスは不要のため、prod / dev とも4項目すべて有効化した。

### 9-5. アプリ側の不可逆操作の是正（推奨）

3-3 の3件。バックアップで救済はできるが、そもそも壊さない実装にする方が復旧コストがかからない。`docs/role-design.md` Phase 3 の `original_path` 対応と併せて検討する。

## 10. 個人情報・肖像権との整合

本アプリは未成年を含む肖像（`images.consent_status`）と、体験申し込みの個人情報（氏名・生年月日・電話番号・学校名）を扱う。**バックアップは「消したはずのデータが残り続ける」仕組みでもある**ため、保持期間の設計は保護と削除義務の両立で決める。

### 方針

1. **バックアップからの個別削除は行わない。** 過去の断面を後から改変することはバックアップの整合性を壊し、他のデータの復旧可能性を損なうため。これは一般的な実務上の整理でもある。
2. 代わりに**保持期間の上限を明示する**。本設計では最長 **35日**（weekly ダンプ）で、削除したデータはバックアップからも確実に消滅する。
3. 掲載取り下げ・削除の依頼を受けた場合は、**本番データからの削除日**と**バックアップからの消滅予定日（削除日＋35日）**を記録し、依頼者に説明できる状態にする。
4. バックアップから復元した際は、**復元後に「復元時点以降に削除されたデータ」を再削除する手順**を必ず実行する。削除依頼に応じたデータが復元で復活する事故を防ぐため、削除依頼の記録は DB のバックアップとは別に管理する（13-1 #3。Google スプレッドシートで管理する）。

**35日は 13章 #2 で決定した値**（当初案の90日から短縮）。個人情報の残存期間を短くすることを優先し、長期の遡及可能性を手放した。
35日を超えて遡る必要が生じた場合、戻せるのは「35日前の断面」までである点を運用ルールとして共有しておくこと。

### T5-2. 【重要】Governance モードは特権ユーザーが迂回できる

検証したところ、`--bypass-governance-retention` を付けると**root 権限では削除できてしまった**。

```
aws s3api delete-object --bucket <dump-bucket> --key <key> \
  --version-id <id> --bypass-governance-retention   → 削除に成功した
```

つまり **Governance モードは「うっかり削除」は防ぐが、「鍵を奪った攻撃者による意図的な削除」は防げない**。本書が想定するシナリオ（root キー漏洩・ランサムウェア）に対しては不十分である。

| モード | 誰が消せるか | 向き・不向き |
|---|---|---|
| **Governance**（現状） | `s3:BypassGovernanceRetention` を持つ者は消せる。root は常に該当 | 誤操作対策としては有効。**攻撃者には無力** |
| **Compliance** | **誰も消せない**（rootでも、AWSサポートでも不可） | 攻撃者にも耐える。ただし**取り消しが一切効かない** |

Compliance にすると、間違ってアップロードしたデータも保持期間が切れるまで消せず、その分の保管料も発生し続ける。保持期間が最長35日と短いため、実害は限定的と考えられる。

**判断が必要**: 大阪（オフサイト）側だけ Compliance にするのが妥当か。→ 未決

#### #1 の補足 — なぜ Resend ではなく SNS か

アプリは既に Resend でメールを送っているが、**バックアップ失敗の通知にアプリの送信経路を使ってはいけない**。

理由は単純で、**知らせたい障害の多くは、アプリ自身が動かない障害**だから。ECS が落ちている・DB に繋がらない・リージョンが死んでいる、という状況で「アプリ経由でメールを送る」仕組みは同時に沈む。監視の通知経路は、監視対象と独立していなければ意味がない。

SNS は AWS 側で完結し、ECS もアプリも介さない。メール通知は月1,000件まで無料で、本用途では上限に当たらない。

```bash
# トピックを作り、宛先を1件ずつ登録する（各アドレスに確認メールが届き、本人が承認して有効化される）
aws sns create-topic --name blazeapp-backup-alerts --region ap-northeast-1

aws sns subscribe \
  --topic-arn <上で得た ARN> \
  --protocol email \
  --notification-endpoint you@example.com \
  --region ap-northeast-1
```

宛先を2〜3件にする狙いは**単一障害点の回避**。1件だと、そのアドレスが受信できない状態（迷惑メール判定、容量超過、退職・機種変更）になった瞬間に監視が黙って死ぬ。**うち1件は普段使っていないアドレス（別ドメイン・別プロバイダ）にする**と、ドメイン単位の障害にも耐えられる。

なお SNS のメールは Subject や本文の書式をほとんど制御できない。読みやすさより「確実に届くこと」を優先した選択である。

#### #3 の補足 — なぜ DB の外に置くのか

**何のための記録か**: バックアップから復元すると「削除したはずのデータ」が一緒に復活する。掲載取り下げ依頼に応じて消した写真が、復旧作業のあとに再び公開されている——これは謝罪では済まない事故になり得る。だから復元後に「もう一度消すべきもの」の一覧が要る。

**なぜ DB に置けないか**: 記録を DB に置くと、その記録自身も復元で巻き戻る。「何を消すべきか」を書いたリストが、消す前の状態に戻ってしまっては役に立たない。

**記録する項目**: 対象（画像ID / 申込ID等）・依頼日・本番からの削除日・バックアップからの消滅予定日（削除日＋35日）・依頼者への回答状況。

**運用ルール**: `PATCH /api/consent-requests/:id` で `accepted` にしたら、**その場でシートに1行足す**。この2つを必ずセットで行う。

この記録の価値は「網羅性」より「復元時に必ず参照されること」にあるため、開いてすぐ読める形を優先した。発生件数が増えて手入力が負担になったら、削除処理からS3へ自動追記する方式へ移行してよい（現状の想定は年に数件）。

#### #4 の補足 — なぜ AWS の外に置くのか

**現状の問題**: `infra/scripts/create-secret.sh` は「実行者が値を持っていること」を前提にしている。つまり値は誰かの頭の中かローカルにしかない。シナリオ B・C（DB全損・リージョン障害）では `DATABASE_URL` の書き換えが必要で、**値が分からないと復旧が止まる**。

**対象**: DB パスワード、`RESEND_API_KEY`、`JWT_SECRET` 等（`SECRET_ENV_KEYS` の全項目）、AWS のログイン情報、Vercel トークン。

Secrets Manager の値をそのまま正とする案は、**AWS アカウントを失った時に何も分からなくなる**ため採らない。3-2-1 の思想（1つはオフサイト）は認証情報にも当てはまる。

**更新タイミング**: `create-secret.sh` を実行したら**必ず同時に Bitwarden も更新する**。実行とセットにするのが最も忘れにくい。

**最後の単一障害点への備え**: Bitwarden 自体からロックアウトされると全てが止まる。マスターパスワードと復旧コードは紙に書いて物理的に保管し、緊急アクセス権限（信頼できる第三者が一定時間後にアクセスできる機能）も設定しておく。

#### #6 の補足 — 大阪へ直接書かない理由

RDS を CDK の VPC 内へ移す（9-2）と、ECS タスクはプライベートサブネットに入る。ここから S3 へ書くための経路が論点だった。

当初は「大阪のバケットへ直接書く」構成にしていたが、**S3 Gateway エンドポイント（無料）は同一リージョンにしか到達できない**。大阪へ直接書くには NAT ゲートウェイ（月$35〜40）か Interface エンドポイントが必要になり、月額$4〜5 の設計に対して不釣り合いなコストになる。

そこで**東京のバケットに書き、S3 レプリケーションで大阪へ複製する**構成に変更した。

- Gateway エンドポイント（無料）だけで完結し、**NAT ゲートウェイは不要**
- レプリケーションは 5-3 の画像で既に使う仕組みであり、新しい要素を増やさずに済む
- 大阪に届くまで数分のラグが出るが、**二次 RPO 1時間に対して十分な余裕**がある

副次的な効果として、東京にもダンプが残るため、リージョン障害以外の復旧では大阪を経由せずに済む（転送料と手間が減る）。

なお**東京バケットにも Object Lock を掛ける**こと。複製元が消せてしまうと、イミュータブル（3-2-1-1-0 の「1」）が片側でしか成立しない。

### 13-2. 単独運用であることの含意（#5 の決定を受けて）

復旧を owner 本人が行うと決めた以上、**その人が対応できない状況が単一障害点**になる。設計としてこれを補う。

| リスク | 対策 |
|---|---|
| 障害に気づけない | 通知先2〜3件のうち1件を**スマートフォンで即座に気づくアドレス**にする |
| 手順を忘れる | 7章の手順を**そのままコピペで実行できる粒度**に保つ（本書の現状の書き方を維持する） |
| 実施者が不在 | 8章の四半期訓練で**手順書だけを見て復旧できるか**を確認する。詰まった箇所は手順書の不足として書き足す |
| 認証情報にアクセスできない | Bitwarden の**緊急アクセス権限**（信頼できる第三者が一定時間後にアクセスできる機能）を設定する |

**将来 admin が増えた場合**は #5 を再検討し、副担当を決めること。
