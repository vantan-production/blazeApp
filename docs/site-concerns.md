## A. リリース前に必ず潰す技術的ブロッカー

### A-1. HTTPS と独自ドメインが無く、現状の設計ではログインが成立しない ★最重要

**現状（コード上の事実）**

| 箇所 | 内容 |
|---|---|
| `infra/lib/backend-stack.ts:102` | ALB は `listenerPort: 80`。ACM 証明書の指定なし ＝ **API は http のみ** |
| `back/src/admin/login.ts:143` | Cookie を `HttpOnly; Secure; SameSite=Strict` で発行 |
| 現行の配置 | フロント: Vercel（`*.vercel.app`, https） / API: ALB（`*.elb.amazonaws.com`, http） |

**何が起きるか（3つ同時に詰む）**

1. `Secure` 属性の Cookie は **http の応答では保存されない**。
2. https のページから http の API を呼ぶのは **mixed content でブラウザが遮断する**。
3. 仮に https 化しても、`vercel.app` と `elb.amazonaws.com` は**別サイト**であり、`SameSite=Strict` の Cookie は**送信されない**（`vercel.app` は Public Suffix List 登録ドメインのため、サブドメインを揃えても同一サイトにならない）。iOS Safari は特に厳しい。

**決めること**

- 独自ドメインを取得し、**フロントと API を同一の登録可能ドメイン配下に置く**（例: `nishioblaze.jp` と `api.nishioblaze.jp`）。これが最も素直で、`SameSite=Strict` を維持したまま解決できる。
- ALB に ACM 証明書を付け、80 は 443 へリダイレクトする。証明書は DNS 検証なら自動更新される。
- 代替案として「Next.js の Route Handler で API をプロキシして同一オリジンにする」もあるが、SSR サーバーを1段挟むぶん遅延とコストが増える。
- ドメインの**取得名義・支払い・更新期限**を誰が持つか（G-2 と連動）。

> この項目は他の全機能の前提である。`docs/role-design.md` の Phase 0〜4 は実装済みだが、**A-1 が解決するまでブラウザからは1つも動かせない。**

### A-2. RDS のネットワークと prod/dev 同居

`docs/backup-design.md` §3-2 / §9-1 / §9-2 に記載済みだが、**バックアップの前提としてではなく「公開前の必須是正」として**再掲する。

- `PubliclyAccessible: true`、SG が `0.0.0.0/0` から 5432 を許可 ＝ 防御はパスワードのみ
- prod と dev が同一インスタンス（DB名違いのみ）＝ dev の事故が prod に波及し、復元も巻き添えになる

体験申し込みには**未成年の氏名・生年月日・電話番号・学校名**が入る（`back/src/db/schema.ts:126-150`）。公開前に是正すること。

### A-3. AWS 認証情報の持ち方

| 箇所 | 現状 | あるべき姿 |
|---|---|---|
| ローカル CLI | root アカウントのアクセスキー | IAM ユーザー／ロールへ移行し root キーは削除（`backup-design.md` §9-3） |
| ECS の S3 アクセス | `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` を Secrets Manager に格納し `back/src/db/s3.ts:19-23` で明示指定 | **タスクロール（IAM）に移行**。受け皿は `infra/lib/backend-stack.ts:134-138` にコメントで用意済み |
| GitHub Actions | OIDC 済み（`deploy.yml`） | 現状のままでよい |

長期キーは失効も追跡もできない。タスクロール化はコード変更が数行で済む（`s3.ts` の `credentials` を消すだけ）。

### A-4. レートリミットのキーが ALB のIPになる

`back/src/utils/monitoring.ts:69` に、ALB 配下では `getConnInfo()` が ALB のIPを返すため `X-Forwarded-For` の右端を使う、という正しい実装（`clientIp()`）がある。

しかし**レートリミッタ側は今も `getConnInfo()` を直接使っている**。

```
back/src/admin/login.ts:35 / register.ts:39 / forgotPassword.ts:31 /
resetPassword.ts:32 / accountRecover.ts:30 / inquiry/index.ts:33 / trial/index.ts:24
```

結果、本番では**全利用者が同一のキーを共有する**。影響が大きい順に:

| API | 制限 | 本番での実挙動 |
|---|:-:|---|
| 問い合わせ | 1回/分 | **サイト全体で1分に1件**しか送れない |
| 体験申し込み | 1回/分 | 同上 |
| ログイン | 5回/分 | 誰かが失敗すると**全員がログインできなくなる** |

対応は `keyGenerator` を `clientIp(c)` に差し替えるだけ。監視の作業と同じファイルを触るため、**まとめて直すのが自然**。

### A-5. 本番での `/docs` 公開可否

`back/src/docs/index.ts:12-14` により `NODE_ENV=production` では既定で無効。ただし `ENABLE_API_DOCS=true` を入れれば本番でも開く。**Scalar UI はログイン中の Cookie をそのまま使って本番 API を叩ける**ため、本番で有効化しない運用ルールを明文化しておくこと。

## C. 個人情報・肖像権・法務 ★HP 特有かつ見落としやすい

本アプリは**未成年を含む個人情報と肖像**を扱う。技術ではなく運用と掲示物の問題であり、コードを書いても解決しない。

### C-1. 保持期間と削除手順が未定義

| データ | 保持の現状 | 未決事項 |
|---|---|---|
| 体験申し込み（氏名・フリガナ・生年月日・性別・学校名・塾名・電話番号） | **無期限**。自動削除の仕組みは無い | 何か月で消すか。入団した子／来なかった子で分けるか |
| 問い合わせ（氏名・メール・本文） | **無期限** | 同上。対応済みから何か月で消すか |
| 退会・卒団した member のアカウント | 削除リクエスト後30日で物理削除（`back/src/app.ts:124`） | 年度替わりに誰が棚卸しするか |
| バックアップ内の個人情報 | 最長35日で消滅 | `backup-design.md` §10 で定義済み。**本番側の削除ルール（本項）とセットで初めて説明可能になる** |

削除依頼を受けたときの記録（削除日・バックアップからの消滅予定日）は `backup-design.md` §10 でスプレッドシート管理と決めているが、**本番データの削除ルール自体が未定**のため、現状は依頼者に説明できない。

### C-2. 掲示が必要な文書が1つも無い

- **プライバシーポリシー／個人情報の取扱いについて**（利用目的、取得項目、第三者提供の有無、保管期間、開示・訂正・削除請求の窓口）

- **運営主体の表記**（団体名・所在地・連絡先）
- 体験申し込みフォーム内の**同意チェック**と、**16歳未満は保護者の同意**を得る導線
- アクセス解析を入れる場合の **Cookie 同意**（入れないなら不要）

### C-3. 肖像権・掲載同意の運用

DB 側は `images.consent_status` とモザイクで設計済みだが、**実際に同意をどう取るか**が未定。

- 入団時に書面で一括同意を取るのか、写真ごとに確認するのか
- 「掲載不可」の子が写り込んだ写真の運用（モザイクは人手。誰が座標を指定するか）
- 卒団後・退部後の掲載継続の可否
- 関係者に配布する**原本（モザイクなし）の再配布禁止**をどう約束させるか（`role-design.md` §12-4 の未決事項と同じ）

### C-4. 著作権

- 掲載する写真・動画の撮影者（保護者が撮った写真の権利）
- 動画に BGM を付ける場合の音源

## E. 可用性・性能・コスト

### E-1. 監視の残タスク（計装は作業中）

`back/src/utils/monitoring.ts` で構造化ログの出力までは実装中。**残っているのは「気づく」仕組み**。

- CloudWatch Logs のメトリクスフィルタ（`SECURITY_EVENT` / `APP_ERROR` を数える）
- アラーム（500 の発生、ログイン失敗の急増、ALB の 5xx、ECS タスクの異常終了、RDS の空き容量）
- 通知先（`backup-design.md` §5-2 では SNS → メール2〜3件で決定済み。同じトピックを流用できる）
- 外形監視（サイトが落ちたことを外から検知する。無料の UptimeRobot 等）
- ログ保持14日で足りるか（`infra/lib/backend-stack.ts:124`）

### E-2. 可用性

| 項目 | 現状 | 論点 |
|---|---|---|
| ECS タスク数 | `desiredCount: 1` | デプロイ中・タスク再起動中は**全断**。2にすると費用は倍 |
| オートスケール | 無し | 大会・入団シーズンのアクセス集中 |
| RDS | Multi-AZ 無効 | `backup-design.md` §5-1 で「RTO 4時間なら不要」と判断済み |
| 外部依存 | Vercel / Upstash(Redis) / Resend / AWS | **Redis が落ちるとレートリミッタが失敗する**。フェイルオープン（制限なしで通す）かクローズ（拒否）かの挙動を確認しておくこと |

### E-3. アップロード処理の性能

| 制約 | 値 | 懸念 |
|---|---|---|
| 1ファイル | 10MB（RAW は 50MB） | `back/src/utils/media.ts:31-34` |
| 1リクエスト合計 | 100MB / 最大10枚 | 試合1日分の写真をまとめて上げると足りない可能性 |
| 変換 | sharp / ffmpeg を**リクエスト内で同期実行** | Fargate 0.5vCPU / 1GB（`backend-stack.ts:96-97`）。動画変換で **ALB のアイドルタイムアウト60秒**を超えうる |
| 失敗時 | `replaceMediaOnS3` は変換前に旧ファイルを削除 | `backup-design.md` §3-3。新旧とも失われる経路がある |

上げ方の運用（何枚ずつ上げるか）を決めるか、非同期化（S3 直アップロード + 後段処理）を検討するか。

### E-4. マイグレーションの自動適用

`back/src/server.ts:13` で**起動時に未適用マイグレーションを自動実行**する。

- タスクを2つ以上にすると**同時実行の競合**が起きうる（E-2 と連動）
- 破壊的な変更を含む場合、デプロイした瞬間に本番へ適用される。**ロールバック手段は `pg_dump` からの復元のみ**
- マイグレーションのレビュー基準を決めるか、適用を手動ステップに分離するかの判断

## F. メール到達性 ★「届かない」と関係者エリアが機能停止する

招待・パスワード再設定・お知らせ通知・体験申し込みの確認と通知が、すべて Resend 経由のメールに依存している（`back/src/utils/mail.ts`）。

| # | 論点 | 現状 |
|:-:|---|---|
| F-1 | 送信ドメインの認証 | 独自ドメイン取得後に Resend でドメイン検証し、**SPF / DKIM / DMARC** を DNS に設定する。未設定だとキャリアメール・Gmail で迷惑メール送りになる |
| F-2 | 送信元アドレスの事故 | `MAIL_FROM` 未設定時は `onboarding@resend.dev` にフォールバックする（`mail.ts:27`）。CDK 側で必須化されているのは prod/dev のデプロイ経路のみ。**フォールバック値のまま本番送信される経路が残っていないか確認すること** |
| F-3 | 無料枠 | Resend の無料枠（1日あたり・月あたりの通数）に対し、member 全員への一斉通知（お知らせ・アンケート）が何通になるか。想定人数（`role-design.md` §12-2 の未決事項）が決まらないと見積もれない |
| F-4 | 届かなかったときの代替 | **招待とパスワード再設定はメールが唯一の経路**。届かない保護者への対応手順（owner が手動で再発行する等）を決めておく |
| F-5 | バウンス・苦情 | 存在しないアドレスへの送信が続くと送信レピュテーションが下がる。Resend 側の通知を誰が見るか |
| F-6 | 通知先の設定漏れ | `TRIAL_NOTIFICATION_EMAIL` 未設定だと**体験申し込みが来ても誰にも通知されない**（CDK は警告のみでデプロイは通る）。設定を運用チェックリストに入れること |
| F-7 | 件名・差出人名 | キャリアメール（docomo/au/softbank）の受信拒否設定に引っかかる可能性。ドメイン指定受信の案内を配布物に載せるか |

## I. 着手順の目安

1. **A-1（ドメイン + HTTPS）** — これが決まらないとフロント実装の土台（Cookie・API URL・CORS）が確定しない。**最初に着手すべき唯一の項目。**
2. **A-2 / A-3 / A-4** — 公開前の必須是正。A-2 は `backup-design.md` §9-1 のインスタンス作り直しと同時に実施すると二度手間にならない。
3. **C-1 / C-2** — 文面の作成には日数がかかる。フロント実装と並行して着手する（ページとして載せる先が要るため、D と同時に完成させる）。
4. **D** — フロント実装。分量が最も大きい。
5. **F** — ドメイン取得（A-1）の直後に DNS 設定として一緒に済ませる。
6. **E-1 / E-5 / G** — 公開直前〜公開後に整える。

## J. クライアントに確認すべきこと（`role-design.md` §12 に無いもの）

1. **独自ドメインを取得するか**。取得済みなら名義と管理者は誰か
2. **公開予定時期**（大会シーズン・入団説明会に合わせるか）
3. **月額運用費（$60〜80 想定）の負担者**と上限
4. **団体としての正式名称・所在地・連絡先**（掲示物に必要）
5. **プライバシーポリシー・利用規約の文面を誰が用意するか**（テンプレートを提示してレビューしてもらう形が現実的）
6. **体験申し込み・問い合わせの個人情報を何か月保持するか**
7. **アクセス解析を入れるか**（Google Analytics 等。入れるなら Cookie 同意が要る）
8. **既存の告知手段（LINE 等）を HP に寄せるのか、併用するのか**
